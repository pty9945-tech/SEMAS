# 배포와 초대 인증

## 현재 상태

이 작업 환경에는 사이트를 공개할 관리형 호스팅 연결, 공개 도메인, 인증 이메일 발송 설정이 제공되지 않았습니다. 로컬 검증용 주소는 공개 배포가 아닙니다. 따라서 공개 HTTPS 배포, 실제 이메일 배달, 배포 후 초대자의 로그인·차단·권한 회수는 아직 검증하지 않았습니다.

현재 제공하는 것은 React 화면, Node 서버, SQLite 초대·세션 저장소, SMTP 비밀번호 없는 이메일 인증, 서버 권한 검사, 배포용 Dockerfile입니다. 테스트 이메일 전송기는 자동 검증에서만 주입합니다. 제품 서버에는 인증을 우회하는 개발 로그인이나 메일함 API가 없습니다.

### 2026-10-15 연결 확인 결과

실제 외부 배포가 가능한지 이 작업 환경에서 다시 확인했습니다. 비밀 값은 출력하거나 소스에 저장하지 않았습니다.

| 확인 대상 | 결과 | 의미 |
| --- | --- | --- |
| 기존 GitHub 저장소 | `git ls-remote --heads origin` 성공, `main`과 `sodam-design-preview` 확인 | 기존 저장소에 소스·시안을 전달할 수 있습니다. 저장소 페이지는 상담 사이트 배포가 아닙니다. |
| GitHub 관리 API | 저장소 조회가 네트워크 `Forbidden`으로 실패 | 현재 연결에서 API를 통한 배포 서비스 설정을 할 수 없습니다. |
| 제공된 클라우드 도구 | 환경 초안 읽기·저장 기능만 제공 | 실행 컨테이너의 공개 HTTPS 주소나 영구 호스팅을 발급하는 기능이 없습니다. |
| 연결된 클라우드 계정 | AWS 프로필 없음, Google 자격증명 필드 없음, Azure 인증 설정 없음 | 해당 서비스에 리소스를 생성할 인증 수단이 없습니다. |
| 호스팅 프로젝트 설정 | Render·Railway·Fly·Vercel·Netlify·Cloudflare 프로젝트 바인딩 및 전용 인증 값 없음 | 기존 운영 프로젝트로 배포할 대상이 없습니다. |
| 관리자·메일 설정 | `ADMIN_EMAIL`, `APP_ORIGIN`, `SMTP_*` 미설정 | 관리자 소유권과 실제 이메일 수신을 임의의 값으로 대신할 수 없습니다. |

GitHub Pages와 같은 정적 공개 페이지에는 이 서버의 인증·권한 검사와 SQLite 저장소를 올릴 수 없습니다. 공개 시연 화면을 만들더라도 초대받은 사람만 사용하는 운영 사이트라는 요구를 충족하지 않으므로 대체 배포로 처리하지 않습니다.

## 반드시 필요한 최소 외부 설정

1. 지속 실행되는 Node 24 또는 Docker 서비스와 영구 디스크를 제공하는 호스팅 계정 연결. 서버리스 정적 페이지 호스팅만으로는 이 서버와 SQLite 저장소를 운영할 수 없습니다.
2. 서비스의 공개 HTTPS 주소. 호스팅에서 제공하는 기본 도메인을 사용할 수 있습니다. `APP_ORIGIN`에 정확한 origin(경로 없이)을 지정합니다.
3. 발송 가능한 SMTP 서비스와 검증된 발신 주소. 서비스의 보안 설정에 SMTP 자격증명을 입력합니다. 채팅이나 Git에 비밀번호를 넣지 않습니다.
4. 최초 관리자 본인의 이메일 `ADMIN_EMAIL`. 첫 시작 후 관리 화면에서 초대 이메일을 추가·회수할 수 있습니다.

사이트 사용자는 브라우저와 이메일만 있으면 됩니다. 위 설정은 사이트 운영 환경에 한 번 필요하며, 이용자별 개발 도구 설치는 필요하지 않습니다. 이 환경에 호스팅·이메일 연결이 제공되면 소스 전달부터 배포와 실제 인증 확인까지 이어갈 수 있습니다. GitHub 저장소를 새로 만들 필요는 없습니다.

운영자가 결정해야 하는 값은 최초 관리자 본인의 이메일과 사용할 호스팅·메일 계정입니다. 앱 내부 설정은 `NODE_ENV=production`, `HOST=0.0.0.0`, `PORT=3000`, `DATA_DIR=/data`를 기본으로 사용할 수 있습니다. 호스팅이 발급한 HTTPS 기본 주소를 `APP_ORIGIN`으로 사용하므로 별도 도메인 구매는 필요하지 않습니다. SMTP 서버·발신 주소·인증 값은 실제 발송 서비스가 발급한 값을 사용해야 합니다. 이 연결 전에는 클릭해서 로그인할 수 있는 운영 HTTPS 링크를 발급했다고 안내하지 않습니다.

## 배포 설정

| 변수 | 용도 |
| --- | --- |
| `NODE_ENV=production` | HTTPS·보안 쿠키를 사용하는 운영 모드 |
| `HOST=0.0.0.0`, `PORT=3000` | 컨테이너 수신 주소·포트 |
| `APP_ORIGIN=https://발급된도메인` | 허용 요청 origin·사이트 주소 |
| `DATA_DIR=/data` | 영구 볼륨 경로. SQLite 인증 데이터만 저장 |
| `ADMIN_EMAIL` | 최초 관리자 이메일 |
| `SMTP_HOST`, `SMTP_PORT` | SMTP 발송 서버·포트 |
| `SMTP_SECURE` | 465 implicit TLS는 `true`, 587 STARTTLS는 `false` |
| `SMTP_USER`, `SMTP_PASS` | 제공자가 요구하는 SMTP 자격증명 |
| `SMTP_FROM` | 검증된 발신 이메일 주소 |
| `TRUST_PROXY` | 기본 `0`. 정확히 한 단계의 신뢰하는 역방향 프록시 뒤라면 `1` |

Docker 빌드: `docker build -t sodam .`. 컨테이너에 환경변수를 안전하게 공급하고 `/data`에 영구 디스크를 연결합니다. 프록시에서 HTTPS를 종료하고 포트 3000으로 전달합니다. 단일 인스턴스로 실행합니다. 여러 인스턴스 확장은 공유 데이터베이스로 전환하는 별도 작업이 필요합니다.

현재 클라우드처럼 전용 HTTPS 프록시와 신뢰 인증서를 쓰는 환경에서는 `bash scripts/build-cloud.sh`로 빌드합니다. 기존 프록시를 빌드에도 전달하고, 프록시 이름 해석을 보완하며, 인증서는 BuildKit 임시 secret mount로만 사용합니다. TLS·패키지 무결성 검증은 유지합니다. 프록시 값이나 인증서를 운영 이미지에 저장하지 않습니다. 이 보조 명령은 일반 호스팅에서는 필요하지 않습니다.

한 단계의 역방향 프록시를 쓴다면 `TRUST_PROXY=1`로 설정해야 이용자별 IP 요청 제한이 동작합니다. 이 경우 앱의 포트 3000에는 그 프록시만 접근할 수 있도록 하고 프록시가 전달 IP 헤더를 덮어쓰도록 설정합니다. 직접 인터넷에 노출된 앱에서 이 옵션을 켜면 전달 헤더를 신뢰할 수 없습니다. 두 단계 이상 프록시 환경은 실제 신뢰 체인 설정을 별도로 확인해야 합니다.

헬스체크는 `GET /healthz`입니다. TLS 인증서 검증을 끄지 마세요. 인증 DB에는 이메일, 권한, 해시된 세션과 인증번호 데이터가 있으며 백업 접근도 제한해야 합니다. 상담 답변·결과는 저장하지 않습니다. 외부 프록시나 호스팅에서 요청 본문과 쿠키를 기록하도록 설정하지 마세요.

## 배포 후 반드시 수행할 확인

1. HTTPS 주소에서 관리자 이메일로 인증번호를 요청하고 실제 받은 번호로 로그인합니다.
2. 관리자 화면에서 확인용 수신 가능한 이메일을 추가합니다. 해당 이용자가 새 브라우저에서 인증하고 상담할 수 있는지 확인합니다.
3. 초대하지 않은 이메일은 인증 메일을 받지 않고 상담 API는 401을 반환하는지 확인합니다. 인증 요청 응답은 초대 여부를 공개하지 않는 같은 문구입니다.
4. 초대받은 일반 이용자의 관리자 API 요청이 403인지 확인합니다.
5. 관리자 화면에서 초대 이용자를 회수하고, 이미 열린 이용자 세션에서 다음 요청이 401인지 확인합니다. 화면도 주기적 세션 확인과 포커스 복귀 시 초기화되어야 합니다.
6. 만료·재사용 인증번호의 실패, 로그아웃 후 차단, 모바일 화면을 확인합니다.

자동 검증에서는 동일한 권한 로직을 테스트 SMTP 대체 전송기로 실행합니다. 이는 실제 호스팅과 이메일 배달 검증을 대신하지 않습니다.

## 정책자료와 접수 상태

2026-10-15에 전달된 2026년 신청안내·운용지침 자료는 조건표와 질문 분기표의 근거로 사용합니다. 자료별 반영 범위와 검증 내역은 `docs/source-review.md`, `docs/conditions.md`, `docs/validation.md`에서 확인합니다. 자료를 반영해도 현재 접수 중인지와 실제 심사 결과는 별도 확인 사항입니다. 자료의 적용과 운영 호스팅 연결은 각각 확인해야 하며, 정책자료가 확보되었다고 배포가 완료되는 것은 아닙니다.
